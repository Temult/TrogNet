2. Separately establish current provider eligibility for the intended host, Pro entitlement, credits disabled, owner-only Access policy and policy expiry. 3. Prepare an owner-only local directory (POSIX mode 0700; Windows protected ACL permitting only owner, SYSTEM and administrators). Persist a dedicated UUID URN as BROKER_HOST_ID. Supply the encryption key through the protected process environment named TROGNET_TOKEN_ENCRYPTION_KEY. Do not place credentials in config, logs or support packages. Do not use browser cookies, another client or Codex credentials.
4. First enrollment config omits PLAN_CLIENT_ID, PLAN_OWNER_SUBJECT and PLAN_WORKSPACE_ID. Owner email is an independent admission policy, not a workspace identifier. Retain host.json between attempts. Live CLI is explicit: node scripts/oss-bootstrap.mjs --live <private-config> <private-publication-attestation> <owner-only-directory>. This command is prohibited during local qualification.
5. The callback must pass state/client validation. pending.json is durably saved before exchange; it contains only schema, host ID and issued client ID. Denial or bad state saves nothing. Exchange failure or interruption leaves pending separate from active. Do not replay a consumed code or delete pending to force another registration. Start a fresh explicit authorization attempt using the retained client ID. A crash leaves enrollment.lock: verify no helper is running and reconcile the attempted operation before removing that single stale lock. Never remove active identity to switch accounts.
6. The newly signed ID token establishes issuer and subject after signature, audience, nonce, expiry and scope checks. Review the verified identity in the local terminal and type CONFIRM. Declining leaves prior active state unchanged. No unverified workspace extension is required or interpreted. The provider binds the issued registration to the selected workspace; this software does not independently verify a workspace claim.
7. active.json atomically stores the verified registration, encrypted ID-token hint and sealed broker-transfer bundle. It contains no plaintext token. Returning authorization uses exactly the same host, client, issuer and subject. A retained hint can be expired; it never replaces validation of the new signed ID token. Do not copy browser authorization URLs into logs: redactAuthorization removes hint, state, nonce and PKCE fields. Never send retained ID tokens to model inputs or ordinary frontend state.
8. Only after a separate live-import authorization: set the learned client/subject in private broker/import config. Bind epoch, digest and short expiry to the sealed bundle, require owner Access and the temporary import secret, open the existing one-use aperture, and import active.json with oss-import.mjs. Match the broker receipt epoch and digest. Close the aperture and verify closure. Ambiguous results freeze the operation; inspect broker status before any exact replay. No automatic retry or new session is allowed.
9. After verified receipt and closure, run node scripts/oss-bootstrap.mjs --forget-transfer <owner-only-directory> and type IMPORT_CONFIRMED. This removes only the transfer copy; encrypted hint and registration remain. Reauthorization requires a reconciled broker epoch and state. Never overwrite unresolved transfer state.
10. Enrollment and one-shot probing are distinct from unattended service. Two sanitized live grants qualify earliest_refresh_at as Unix seconds; the official reference still does not specify units. Code and refresh grants share a strict safe-integer conversion to milliseconds, accepting only a positive timestamp strictly before access expiry with at most 15 minutes lead. Missing schedules stay absent; malformed schedules reject the grant. Legacy unqualified_refresh_schedule records still block renewal and require owner reconciliation using the latest session, never an older laptop bundle.
11. BrokerCore renews on demand within two minutes of expiry, respecting the provider earliest time; expired access does not prevent renewal while the refresh token is valid. Successful refresh requires the documented expires_in of 3600, a different nonempty refresh token, and required scopes. The replacement is sealed and durably staged as one token set before becoming ready. A staged replacement survives restart; failed write acknowledgements never restore the consumed token. One authoritative broker writer per session remains required.
12. Confirmed terminal refresh codes clear tokens and require reauthorization with the saved issued client ID. invalid_client freezes configuration for owner correction. Proven DNS/connect-refusal failures retain credentials with a durable 30-second retry-not-before; retries occur only on a later getToken call. Timeouts, resets, malformed success responses, temporary HTTP errors and unknown outcomes preserve sealed credentials in refreshing and require owner reconciliation or reauthorization. The reviewed docs do not establish safe rotating-token replay after dispatch, even for 5xx. Do not manually reset refreshing to ready or replay an old token.
